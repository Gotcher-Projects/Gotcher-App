Stripe, for the CradleHQ subscription

What Stripe is, what you set up on the business side, and what the code does — for the Plus $4.99/month subscription we're about to build. Written against our actual plan, not a generic tutorial.

Customer→ Stripe Checkout→ Subscription→ Webhook→ CradleHQ grants Plus

1What Stripe is

The payment company that lets a website charge cards and run subscriptions.

Stripe is the plumbing between a customer's credit card and our bank account. We never see or store a card number — the customer types it into a page Stripe hosts, Stripe charges it every month, and Stripe deposits the money into the LLC's bank account. Our job is just to tell Stripe "start a $4.99/month subscription for this person," and then to listen for Stripe telling us "they paid — turn on their Plus features."

The subscription mental model

Five Stripe objects, in the order they come to life. Learn these five words and the rest of Stripe reads easily:

ObjectWhat it isIn CradleHQ
CustomerA person Stripe knows, tied to an email + saved card.One per registered user, created the first time they upgrade. We store its cus_… id.
ProductA thing you sell.A single product named "Plus."
PriceHow much a product costs + how often.$4.99, recurring monthly. Has a price_… id the code references.
SubscriptionA live agreement: this customer pays this price on a cycle.Created when they check out; its sub_… id lives on the user row.
InvoiceOne bill in the cycle — created & paid automatically each month.Every successful monthly invoice is our signal to refill their 10 AI credits.
The key ideaYou don't build a billing engine. You create a Price once, send people to Stripe's Checkout, and react to the events Stripe sends back. That's the whole integration.

3Money flow

Stripe is the money-IN account. (Lulu, later, is money-OUT.)

Customer's card  →  Stripe (charges $4.99, keeps a small fee)  →  payout to the LLC bank account.

Because customers pay us through Stripe, the LLC is the merchant of record. This is the same account that will later fund physical books: when a customer orders a printed storybook, they pay us here via Stripe, and we separately pay the printer (Lulu) on a company card. See the Lulu explainer for that side.

4Owner  What you set up

The account work only you can do — it needs the LLC's legal, tax, and bank details.

None of this touches code. It's account creation in Stripe's dashboard, plus copying a few keys back to the developer. The detailed, non-technical walkthrough is in handoffs/stripe-account-handoff.md — this is the summary so you know why each step exists.

  1. Create the Stripe account under the LLC — business email, account type Company / LLC, legal name, address, EIN.
  2. Identity + bank — enter a company representative's ID details (Stripe legally needs a real person) and link the LLC bank account for payouts.
  3. Activate — Stripe reviews the account. This can take a few days. The developer isn't blocked meanwhile — test mode works immediately (see §7).
  4. Create the product + price — a product named "Plus," recurring $4.99/month, in live mode. Copy the resulting price_… id.
  5. Add the webhook endpoint — the developer gives you a URL (e.g. https://cradlehq.app/billing/webhook); add it and copy the signing secret whsec_….
  6. Grab the live secret key — Developers → API keys → sk_live_….
  7. Invite the developer as a team member so they can pull test keys themselves.

The keys you hand back — and how to read them

Stripe keys are prefixed so you always know what you're holding. Test keys are safe to share; live and signing secrets are not — send those via a one-time self-destructing link (Onetime Secret), never plain email.

Looks likeWhat it isSecret?
sk_test_…Secret key, test mode — fake money, developer self-serves.Low — test only
sk_live_…Secret key, live mode — charges real cards.Yes — guard it
pk_…Publishable key — safe to expose in a browser. (We barely use it with hosted checkout.)No
whsec_…Webhook signing secret — proves an incoming event is really from Stripe.Yes
price_…The id of the Plus $4.99 price.No — plain email is fine
Owner takeawayEverything on this side has a test twin and a live twin. The developer builds against the test twins for weeks; you only produce the live ones (steps 4–6) once, when we're ready to charge real customers.

5Dev  What the code does

A new com.gotcherapp.api.billing package with four endpoints, plus one migration.

EndpointAuthDoes
POST /billing/checkoutJWTCreates a Stripe Checkout Session for Plus; returns the URL to redirect to.
POST /billing/webhookPublicStripe calls this. Verifies the signature, then updates the user's tier/credits.
GET /billing/portalJWTCreates a Billing Portal session; returns the URL for self-serve cancel/manage.
GET /billing/statusJWTReturns tier, credits remaining, reset date, grace status for the UI.

The webhook is the heart of it. Stripe sends an event; the handler maps it to a database change:

Stripe eventWhat the code does
checkout.session.completedSet tier='plus', store stripe_customer_id + stripe_subscription_id, set credits to 10, clear grace.
invoice.payment_succeededMonthly renewal — reset credits to 10, clear any grace flag.
invoice.payment_failedSet tier_grace_until = now + 3 days (don't downgrade yet).
customer.subscription.deletedSet tier='free', clear the subscription id. Keep all their content.

Config the developer adds — the V32 migration (new Stripe columns on users) and three env vars:

envBackend/.env
STRIPE_SECRET_KEY=sk_test_…          # sk_live_… in production
STRIPE_WEBHOOK_SECRET=whsec_…
STRIPE_PRICE_PLUS_MONTHLY=price_…

① Create a Checkout Session POST /billing/checkout

JavaBillingService.java
// Stripe.apiKey is set once at startup from STRIPE_SECRET_KEY.
public String createCheckoutSession(long userId) throws StripeException {
    User user = users.findById(userId);

    // Reuse the Stripe customer if we've made one before.
    String customerId = user.stripeCustomerId();
    if (customerId == null) {
        Customer c = Customer.create(
            CustomerCreateParams.builder()
                .setEmail(user.email())
                .build());
        customerId = c.getId();
        users.setStripeCustomerId(userId, customerId);   // JdbcTemplate UPDATE
    }

    SessionCreateParams params = SessionCreateParams.builder()
        .setMode(SessionCreateParams.Mode.SUBSCRIPTION)
        .setCustomer(customerId)
        .addLineItem(SessionCreateParams.LineItem.builder()
            .setPrice(plusPriceId)        // STRIPE_PRICE_PLUS_MONTHLY
            .setQuantity(1L).build())
        .setClientReferenceId(String.valueOf(userId))  // so the webhook knows who
        .setSuccessUrl(appBaseUrl + "/upgrade-success?session_id={CHECKOUT_SESSION_ID}")
        .setCancelUrl(appBaseUrl + "/book")
        .build();

    return Session.create(params).getUrl();   // hand this URL to the frontend
}

② Verify + handle the webhook POST /billing/webhook

JavaBillingController.java
@PostMapping(value = "/webhook", consumes = "application/json")
public ResponseEntity<String> webhook(
        @RequestBody String payload,
        @RequestHeader("Stripe-Signature") String sig) {
    Event event;
    try {
        // Rejects anything not signed with our whsec_ secret.
        event = Webhook.constructEvent(payload, sig, webhookSecret);
    } catch (SignatureVerificationException e) {
        return ResponseEntity.badRequest().body("bad signature");
    }

    StripeObject obj = event.getDataObjectDeserializer().getObject().orElse(null);
    switch (event.getType()) {
        case "checkout.session.completed" -> billing.activatePlus((Session) obj);
        case "invoice.payment_succeeded" -> billing.refillCredits((Invoice) obj);
        case "invoice.payment_failed"    -> billing.startGrace((Invoice) obj);
        case "customer.subscription.deleted" -> billing.downgrade((Subscription) obj);
        default -> { /* ignore — still 200 so Stripe doesn't retry */ }
    }
    return ResponseEntity.ok("ok");   // ALWAYS 200 for handled events
}
Return 200 — alwaysAny non-2xx (or an uncaught exception) makes Stripe retry the event for days. Handle what you know, ignore the rest, and return 200. Keep the work fast; do nothing that can hang.

③ Billing Portal (self-serve cancel) GET /billing/portal

JavaBillingService.java
import com.stripe.model.billingportal.Session;
import com.stripe.param.billingportal.SessionCreateParams;

public String portalUrl(long userId) throws StripeException {
    String customerId = users.findById(userId).stripeCustomerId();
    Session s = Session.create(SessionCreateParams.builder()
        .setCustomer(customerId)
        .setReturnUrl(appBaseUrl + "/book")
        .build());
    return s.getUrl();   // cancel, update card, view invoices — all hosted by Stripe
}

Local webhooks with the Stripe CLI

Webhooks can't reach localhost from the internet, so the Stripe CLI tunnels them — and it prints a webhook signing secret to use locally:

bash
stripe listen --forward-to localhost:3001/billing/webhook
# → prints:  Your webhook signing secret is whsec_… (use it as STRIPE_WEBHOOK_SECRET locally)

# In another terminal, fire a fake event:
stripe trigger checkout.session.completed
Rollout orderShip the backend to production in test mode first and confirm webhooks land. Only flip STRIPE_SECRET_KEY to sk_live_… once the whole flow is verified end-to-end.

8Security notes

  • Verify every webhook. The endpoint is public — anyone can POST to it. Webhook.constructEvent with the whsec_ secret is what proves the event actually came from Stripe. Without it, a stranger could POST a fake "payment succeeded" and get Plus for free.
  • Secret keys never touch the browser. sk_live_… and whsec_… live only in the server's environment — never in JSX, never in a committed file. Hosted Checkout means the client only ever handles a redirect URL.
  • Add /billing/webhook to the public list in SecurityConfig — it has no JWT (Stripe isn't logged in). Everything else under /billing/** stays JWT-protected.
CradleHQ gotcha · the 401 trapAn uncaught RuntimeException in a Spring controller re-dispatches to /error unauthenticated and surfaces as a 401, not a 500 — which looks like an auth bug when it's really a Stripe error. In every billing endpoint, catch Exception (not just StripeException) and return a mapped ApiError. This is already burned into us from the Cloudinary work.

10Glossary

Customer
A person Stripe knows — an email plus saved payment method, identified by a cus_… id. One per upgraded user.
Product vs Price
The product is what you sell ("Plus"); the price is how much and how often ($4.99/month, id price_…). One product can have many prices; we have one.
Subscription
A live recurring agreement between a customer and a price. Its sub_… id lives on our user row while Plus is active.
Invoice
A single bill Stripe generates and charges each cycle. A paid invoice each month is our cue to refill credits.
Webhook
An HTTP POST Stripe makes to us when something happens (payment succeeded, subscription cancelled). How our database learns about billing events.
Signing secret (whsec_)
A shared secret used to cryptographically verify a webhook really came from Stripe and wasn't forged.
Idempotency
Designing a handler so processing the same event twice is harmless — important because Stripe may deliver an event more than once.
Publishable vs secret key
pk_… is safe in a browser; sk_… can charge cards and must stay server-side. Each has a test and a live variant.
Billing Portal
A Stripe-hosted page where customers cancel, swap cards, and view invoices — so we build no cancel UI.
Grace period
Our 3-day window after a failed payment before downgrading, giving the customer time to fix their card.
