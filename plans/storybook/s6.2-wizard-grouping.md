## Context

S6.1 laid the data and template foundation. This session adds the wizard grouping step — the core of the scrapbooking UX. Users see their selected memories as cards and arrange them into page groups. The system suggests groupings for short memories. Each page group gets a template and photo assignments. The wizard then generates AI content for each group and builds the `layout_data` automatically.

The existing mode picker (Step 3: "One Story" vs "One Page Per Memory") is replaced. "One Story" (single narrative) stays as-is. "Memory Pages" now routes through the new grouping step before generation.

The LayoutEditor is not removed — but the new path does not route to it. Users who reach the layout editor through the old path still can.

---

## New Wizard Flow (Memory Pages path)

```
Step 1 — Period selection (unchanged)
Step 2 — Memory selection + photo overrides + notes (unchanged)
Step 3 — Mode picker: "Single Story" vs "Memory Pages" (updated label only)
  └─ Single Story → Step 4 (supplementary notes) → generate → Step 5 (review) → existing layout
  └─ Memory Pages → NEW Step 3.5 (grouping) → generate → book renders in StorybookTab
Step 3.5 — NEW: Page Grouping (Memory Pages only)
```

## Step 3.5 — Page Grouping UI

### Layout

A two-panel view:
- **Left panel** — "Memories" pool: cards for all selected memories (journal entries + first times), not yet assigned to a page
- **Right panel** — "Pages" list: page slots the user builds up; each slot shows its assigned memories, template selector, and photo slot assignments

On first entering Step 3.5, the system **auto-suggests** an initial grouping (see Auto-Suggest below) and populates the pages list. The user can then drag cards to reorganize.

### Memory card
Shows: date, type badge (Journal / First Time), first ~20 words of text, thumbnail if a photo is available. Word count displayed as a subtle chip — helps user judge whether memories should be grouped.

### Page slot
Each slot shows:
- An ordered list of assigned memory cards (drag to add/remove)
- A template selector — shows only compatible templates (matching `memoryCount` and available photos). The system pre-selects the best match.
- Photo slot assignments — for each photo slot in the chosen template, a small picker showing available photos from the assigned memories + the chapter photo pool. Uses existing `pickPhoto()` for uploads.
- A "Remove page" button (only if 2+ pages exist)

### Controls
- **"Add page"** button — appends a new empty page slot
- **"Generate"** button — proceeds when every page slot has at least one memory assigned

### Auto-Suggest Algorithm
Run when the user enters Step 3.5. Produces the initial grouping:

1. Sort memories chronologically
2. Classify each as "short" if its source text is ≤ 80 words (or if it is a first_time entry with no custom note)
3. Group consecutive short memories together, up to 3 per page
4. Each "long" memory (> 80 words) gets its own page
5. For each page, select the best template:
   - Count photos available across the grouped memories
   - Match to the template with the highest `maxPhotos ≤ available` and correct `memoryCount`
   - Prefer templates with photos over text-only when photos exist
6. Pre-assign photos: first available photo from each memory → that memory's photo slot in the template

This is a suggestion only — the user sees it and can reorganize freely.

## Generation Changes

When the user clicks "Generate" from Step 3.5:

**Backend — new endpoint or extended existing:**

`POST /storybook/generate-pages/{id}` receives a new optional body:
```json
{
  "groups": [
    {
      "pageId": "page-0",
      "sourceKeys": ["journal:42"],
      "templateId": "classic",
      "photoAssignments": { "journal:42": ["url-or-null"] }
    },
    {
      "pageId": "page-1",
      "sourceKeys": ["journal:55", "first_time:7"],
      "templateId": "two-up-both",
      "photoAssignments": { "journal:55": ["url1"], "first_time:7": ["url2"] }
    }
  ]
}
```

If `groups` is absent, the endpoint behaves as before (one page per memory, backward compatible).

**`StorybookService.java`** — `generatePages()` with groups:
- For single-memory groups, prompt is unchanged (90–160 word body)
- For multi-memory groups, adjust the prompt: tell the AI these memories share a page; request shorter `body` (40–70 words each), appropriate `title` and `caption`
- Store results in `generated_content` keyed by sourceKey (as in S6.1)
- Build `layout_data` (v2 format) from the groups + template definitions:
  - For each group, create a page object: `{ id, sourceKeys[], templateId, blocks }`
  - Blocks are built from the template's slot definitions, filled from `generated_content` and `photoAssignments`
  - Store final `layout_data` on the chapter

**`ClaudeClient.java`** — optionally add a `BATCH_PAGES_GROUPED_SYSTEM_PROMPT` for multi-memory pages, or handle via the existing prompt with a length directive per group. Keep it simple — extend the existing prompt rather than a second prompt if possible.

**`GeneratedPageResponse.java`** — no changes needed; generation still returns per-sourceKey content

**`StorybookController.java`** — update `POST /storybook/generate-pages/{id}` to accept optional `groups` body; existing callers (no body) continue to work

Read `StorybookService.java`, `StorybookController.java`, `ClaudeClient.java`, and `StorybookWizard.jsx` before writing any code.

## Frontend — StorybookWizard.jsx Changes

1. **Step 3 label update** — change "One Page Per Memory" to "Memory Pages" (cosmetic only)
2. **New Step 3.5 component** — `PageGroupingStep.jsx` (new file) or inline in wizard; see UI spec above
3. **State for grouping** — `pageGroups` array: `[{ pageId, sourceKeys, templateId, photoAssignments }]`
4. **On Step 3.5 mount** — run auto-suggest algorithm, populate `pageGroups`
5. **On generate** — POST groups to `/storybook/generate-pages/{id}` with the groups body; on success, wizard closes and chapter appears in StorybookTab (same as today for the paged path)
6. **@dnd-kit** — check if `@dnd-kit/core @dnd-kit/sortable @dnd-kit/utilities` are already installed (added in S5.8); install if not

### Photo source for photo-only pages
Photo-only templates (`photo-full`, `photo-two`, `photo-three`, `photo-grid`) have no memory assigned. Their photo slots pull from:
1. The chapter's existing `chapterPhotos` array (uploaded in the wizard via `pickPhoto()`)
2. A new page slot type "Photo page" with no memory — just photo slots + template picker

## layout_data v2 Schema Extension

Pages in the v2 format gain `sourceKeys` (array, replaces singular `sourceKey`) and `templateId`:

```json
{
  "version": 2,
  "pages": [
    {
      "id": "page-0",
      "sourceKeys": ["journal:42"],
      "templateId": "classic",
      "backgroundColor": null,
      "blocks": [ ... ]
    },
    {
      "id": "page-1",
      "sourceKeys": ["journal:55", "first_time:7"],
      "templateId": "two-up-both",
      "backgroundColor": null,
      "blocks": [ ... ]
    }
  ]
}
```

`sourceKey` (singular) on pages remains for backward compatibility with existing v2 layouts — read both, write only `sourceKeys`.
