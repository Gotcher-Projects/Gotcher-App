## Context

S6.2 added the wizard grouping step as the primary path for Memory Pages. This session adds auto-gen mode — a fully automatic path where the system groups memories, picks templates, assigns photos, and generates content without any grouping wizard step. This is the "lazy" path: the user picks memories and clicks generate, and the book builds itself.

Auto-gen uses the same algorithms and endpoints as S6.2, but skips Step 3.5 entirely. The same `groups` payload is built server-side (or client-side before calling the API) using the auto-suggest logic from S6.2.

Also covers: polish, edge cases, and the content preservation fix that was the original S6 scope.

---

## Auto-Gen Mode

### Wizard flow change (Step 3)
The mode picker (Step 3) gains a third option alongside "Single Story" and "Memory Pages (Guided)":

- **Single Story** — one narrative chapter (unchanged)
- **Memory Pages — Guided** — the Step 3.5 grouping wizard (added in S6.2)
- **Memory Pages — Auto** — skip grouping; book generates automatically

"Auto" is positioned as the simpler/faster option, not the recommended one. Labeling suggestion: "Auto (let us decide)" or "Quick Build."

### Auto-gen flow
1. User selects memories in Step 2 (unchanged)
2. User picks "Memory Pages — Auto" in Step 3
3. Wizard shows a loading state ("Building your book…") — no Step 3.5
4. Client runs the auto-suggest algorithm from S6.2 to build `pageGroups`
5. Calls `POST /storybook/generate-pages/{id}` with the `groups` payload (same endpoint as guided path)
6. On success, wizard closes; chapter appears in StorybookTab

The auto-suggest algorithm is already defined in S6.2 — extract it into a shared utility (`src/lib/storybookGrouping.js` or similar) so both the guided step (for seeding initial suggestions) and auto-gen (for the full run) use the same code.

## Content Preservation Fix

This was the original S6 scope — now that the full architecture is in place, wire up content preservation in `applyTemplate()`:

**`LayoutEditor.jsx`** — `applyTemplate()` currently fills text blocks from `cleanBody(chapter.body)`. Update it to:
1. If the page has `generatedContent` in scope (passed from `chapter.generatedContent`), use `generatedContent[page.sourceKeys?.[0] ?? page.sourceKey]?.body` for single-memory text blocks
2. For multi-memory templates, use `generatedContent[sourceKeys[contentSource.memoryIndex]]?.[contentSource.piece]` per block
3. Fallback: `cleanBody(chapter.body)` — for old layouts with no `generatedContent`

This means switching templates no longer wipes per-page AI text.

Also update `StorybookWizard.jsx`'s `buildGeneratedPageBlocks()` — when building the initial page blocks from generated results, pass `generatedContent` through to the page object so `applyTemplate` can access it immediately after generation.

## Polish + Edge Cases

Address any issues surfaced during S6.1 and S6.2 verification:

- **Short memory threshold** — 80 words may need tuning after real-world testing; make it a named constant
- **Template compatibility guard** — when a user assigns a template that requires more photos than are available, show a warning rather than silently producing empty photo slots
- **Photo-only pages without a memory** — confirm the render path handles `sourceKeys: []` gracefully (no `generated_content` lookup, no text blocks expected)
- **Backward compat for `sourceKey` vs `sourceKeys`** — audit `LayoutRenderer.jsx` and anywhere that reads `page.sourceKey`; update to read `page.sourceKeys?.[0] ?? page.sourceKey` consistently
- **Re-generation** — if a user clicks "Regenerate" on a paged chapter that was built via the guided wizard, the grouping should be preserved (stored in `layout_data` as `sourceKeys` + `templateId` per page); only the AI content is regenerated
