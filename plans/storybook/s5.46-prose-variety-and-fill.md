## Overview

Two long-standing complaints with **"One Page Per Memory"** chapters:

1. **Short / photo-less pages waste most of the page** — the prompt targets only 60–100
   words and forbids padding, and `fitText` only ever *shrinks* text, so a short memory
   renders tiny in a full-height box.
2. **Every page opens with "You…" and pages blend together** — `SINGLE_ENTRY_SYSTEM_PROMPT`
   instructs `"You did… / You were…"`, and each page is generated by a **separate,
   independent Claude call**, so pages can't vary their openings relative to one another.

Both live in path 3 (`generate-pages` → `SINGLE_ENTRY_SYSTEM_PROMPT`). The fix has two
prongs: **(a)** change what the model writes (longer, varied openings) by switching paged
generation to a **single batched call** that sees all memories at once, and **(b)** change
how the page renders short text (grow-to-fill + center, content-aware templates).

### Decisions locked with the user
- **Batched call** for paged generation (one call returns all pages as JSON).
- **Keep per-page credit accounting** — still charge 1 credit per selected memory
  (`totalEntries`). No change to the credit model; the batched call is more expensive
  (more context + likely a larger model), so per-page cost stays justified.
- **Add temporary logging** of exactly what we send to Claude and what it returns.
  This is interim observability only → **removed in S9** (`s9-remove-claude-logging.md`).

### Open decision to confirm at implementation
- **Model for the batched call.** Currently `anthropic.model = claude-haiku-4-5-20251001`.
  A multi-page batched prompt may need a stronger model for quality. Default plan: keep the
  single configurable `anthropic.model`, just raise `max_tokens`. If quality is weak, either
  bump the global model or add a separate `anthropic.model.batch` property. Decide after a
  first test run.

## Phase A — Core (resolves both complaints)

### A1. Backend: batched page generation + prompt rewrite

**`ClaudeClient.java`**
- Add `BATCH_PAGES_SYSTEM_PROMPT` (below) and a method
  `String generatePagesBatch(String userPrompt, int maxTokens)` that calls `callClaude(BATCH_PAGES_SYSTEM_PROMPT, userPrompt, maxTokens)`.
- `SINGLE_ENTRY_SYSTEM_PROMPT` + `generateSingle` become unused (only `generatePages`
  called them) — remove them, or keep only if we want a single-page fallback. Default: remove.

```
BATCH_PAGES_SYSTEM_PROMPT (verbatim to implement):

You are composing the pages of a baby's keepsake memory book — one page per memory, in the
order given. Write warmly, in second person addressed to the baby, with a natural
storyteller's voice.

OPENINGS — this is critical: across the whole set, EVERY page must open differently. Never
start two pages the same way, and never begin a page with "You" or with the baby's name.
Rotate among these techniques: a sensory image · the season or the baby's age · a small
sound or near-word · a small action then turn to address the baby · a gentle question ·
direct address with a fresh subject and verb ("Your laugh arrived today.").

LENGTH: each page is 2–3 short paragraphs, about 90–160 words — enough to fill a printed
page without feeling thin. Earn the length; never list or repeat.

YOU MAY: add a gentle reflective beat and lightly evoke the season or the baby's age to
round out a page.
YOU MAY NOT: invent specific events, people, places, spoken words, or feelings not present
in the source. When unsure who was present, write "the people who love you".

STRICT: only reference people/relationships explicitly named; never assume parent count or
gender; never write "your mom/dad/the two of us" unless those exact words appear in the
source; heartfelt and warm, never saccharine; no titles, no photo markers.

For each page also produce a "pullQuote": one short lyrical line drawn from that page
(≤ 12 words).

Return JSON only, no markdown, no preamble:
{ "pages": [ { "sourceKey": "journal:42", "body": "...", "pullQuote": "..." }, ... ] }
```

**`StorybookService.generatePages()`** — replace the per-entry loop with one batched call:
- Keep the tier check and `credits < totalEntries` → `InsufficientCreditsException`.
- **Decrement `totalEntries` credits up front** (single UPDATE). On any failure (HTTP error
  or JSON parse failure) **refund `totalEntries`** and rethrow `RuntimeException` (mirrors the
  existing refund pattern).
- Build **one** user prompt listing every selected memory in date order (reuse the gather
  logic from `appendMergedMemories`: journal `title`/`story`/`week`, first-time `label`/`notes`,
  plus any `wizard_entry_notes`), each tagged with its `sourceKey` so the model echoes it back:
  ```
  Baby: {name}

  Memory — journal:42 — Week 6: "First bath"
  {story}
  Parent's memory: {note}      // if present

  Memory — first_time:9 — "First smile"
  {notes}
  ...
  ```
- `max_tokens`: scale with page count, e.g. `Math.min(800 + totalEntries * 320, <cap>)`.
- Parse the returned JSON `{ "pages": [...] }` with Jackson; map each `sourceKey` →
  `{body, pullQuote}`. Return `List<GeneratedPageResponse>` in date order (same order the
  frontend iterates to build pages).

**`dto/GeneratedPageResponse.java`** — add `String pullQuote` → `{ sourceKey, body, pullQuote }`.

### A2. Backend: temporary Claude logging (removed in S9)

**`ClaudeClient.java`** — in `callClaude(...)`, log the outbound and inbound payloads with a
greppable prefix so S9 can remove it cleanly:
```java
private static final Logger log = LoggerFactory.getLogger(ClaudeClient.class);
// ...inside callClaude, before/after the exchange:
log.info("[CLAUDE-DEBUG] model={} maxTokens={}\n--- SYSTEM ---\n{}\n--- USER ---\n{}",
         model, maxTokens, systemPrompt, userPrompt);
log.info("[CLAUDE-DEBUG] RESPONSE:\n{}", responseText);
```
- Log at INFO so it appears in Docker logs without changing log levels.
- **Privacy note:** these logs contain real journal/first-time content (personal family
  data). This is acceptable *only* as interim debugging — it is the entire reason S9 exists.
  Do not leave it in long-term and do not ship logs anywhere persistent/external.

### A3. Frontend: `fitText` grow-to-fill + vertical centering

**`Frontend/src/lib/fitText.js`** — add a `maxSize` param (defaults to `baseSize`, so existing
callers are unchanged). When `maxSize > baseSize` and the text fits at `baseSize`, binary-search
*upward* to the largest size ≤ `maxSize` that still fits:
```js
export function useFittedFontSize(ref, baseSize, minSize = 8, deps = [], maxSize = baseSize) {
  // if !fits(baseSize) → shrink-search [minSize, baseSize]   (existing behavior)
  // else if maxSize > baseSize → grow-search [baseSize, maxSize]
  // else → baseSize
}
```
- **`LayoutRenderer.jsx`** `RenderedText` and **`LayoutEditor.jsx`** display mode: pass a
  ceiling (e.g. `BASE_FONT * 1.7`) so short text scales up. Editor and renderer must pass the
  **same** `maxSize` so they stay identical.
- Add vertical centering for the text block container (e.g. `flex flex-col justify-center` on
  the `.book-rich` wrapper) so short, grown text sits centered instead of clinging to the top.
  Verify long text still flows/clips correctly (it fills, so centering is a no-op).

## Phase B — Polish (stage after Phase A is verified)

### B1. Content-aware generated-page templates
In `StorybookWizard.handleGeneratePages`, pick the block layout by `(bodyLength bucket × hasPhoto)`
instead of today's fixed split:
- short + photo → hero photo + caption band
- short + no photo → centered "quote card" (large text, generous margins, divider/sticker accent)
- long + photo → photo accent, text dominant (drop cap)
- long + no photo → full-bleed text with drop cap

### B2. Pull-quote + date/age header
- Render the `pullQuote` (large, on short/quote-card pages) and a **date/age header**
  computed in the frontend from the source entry's `week` + `birthdate`
  (e.g. "Spring · 4 months old") — the AI does **not** produce the date label.
- Add these as blocks when building the page, or as page metadata rendered by `LayoutRenderer`.

### B3. Per-page accent rotation
Alternate photo side / a background tint from `theme.palette` / drop-cap on some pages so
consecutive pages read as distinct beats.
