## Phase A — Quick Fixes

### Fix 1: Classic paragraph formatting in text blocks

**Problem:** Text blocks in LayoutEditor display mode show raw plain text. The classic publish view uses styled `font-serif` paragraphs split on `\n\n` — the layout editor should match.

**Fix:** In `LayoutEditor.jsx`, in the text block display section (the part shown when NOT in inline-edit mode), replace the raw text div with the same paragraph rendering used by `LayoutRenderer`:

```jsx
{(block.content || '').split('\n\n').map((para, j) => (
  <p
    key={j}
    className={`font-serif text-foreground/85 leading-snug ${j > 0 ? 'mt-2' : ''}`}
    style={{ fontSize: 'clamp(9px, 1.4vw, 13px)' }}
  >
    {para.trim()}
  </p>
))}
```

**File:** `Frontend/src/components/storybook/LayoutEditor.jsx` — in the `TextBlock` display-mode render.

---

### Fix 2: Photo drag/click conflict — swap button in corner

**Problem:** Clicking anywhere on a photo block opens the swap modal. This fires on the same gesture as the start of a drag, making photo blocks hard to drag without accidentally opening the modal.

**Fix:**
- Remove the `onClick` handler from the photo block container/image itself.
- Add a small swap button (`Camera` icon, ~20×20px) pinned absolute to the top-right corner of the photo block.
- Button has a white semi-transparent pill background and only renders in edit mode (LayoutEditor), never in LayoutRenderer.
- Clicking this button (only) opens the photo swap modal.
- Tapping anywhere else on the block just focuses it for dragging.

```jsx
{/* Inside the photo block, in edit mode only */}
<button
  onPointerDown={e => e.stopPropagation()}
  onClick={() => openPhotoTray(block.id)}
  className="absolute top-1.5 right-1.5 z-20 p-1 rounded-full bg-white/80 shadow-sm"
>
  <Camera className="w-3.5 h-3.5 text-foreground/70" />
</button>
```

`onPointerDown` stops propagation so react-rnd doesn't start a drag when the button is pressed.

**File:** `Frontend/src/components/storybook/LayoutEditor.jsx`

---

### Fix 3: Strip [PHOTO] markers from text block content

**Problem:** The chapter body pre-filled into the first text block contains `[PHOTO:journal:123]` markers. These appear as literal text in the layout editor, which doesn't use inline markers.

**Fix:** Strip markers when initializing text content from `chapter.body`. Apply a regex replace at the point where the body is assigned to the text block's `content` field:

```js
const cleanBody = (body || '').replace(/\[PHOTO:[^\]]+\]/g, '').replace(/\n{3,}/g, '\n\n').trim();
```

Run this in `initBlocks()` (or wherever `chapter.body` is first set as a block's content) and in the "Add Text" handler when pre-filling from the body.

**File:** `Frontend/src/components/storybook/LayoutEditor.jsx`

## Phase B — Multi-Page Chapters

### Overview

A new **optional wizard variant** alongside the existing single-story flow. Users choose their mode at the start of the wizard. The existing flow is unchanged — this is a new path that can eventually become the default.

The feature decomposes into:
1. Layout data format v2 (multi-page JSON schema)
2. LayoutEditor: multi-page canvas (page tabs + add page)
3. LayoutRenderer: page-flip carousel
4. Wizard: new "Page by page" mode variant
5. Backend: per-entry text generation

---

### Layout Data Format v2

Existing v1 format (single page):
```json
{ "version": 1, "blocks": [...] }
```

New v2 format (multi-page):
```json
{
  "version": 2,
  "pages": [
    { "id": "page-0", "sourceKey": "journal:42", "blocks": [...] },
    { "id": "page-1", "sourceKey": "first_time:7", "blocks": [...] }
  ]
}
```

`sourceKey` is optional — tracks which journal/first entry the page was generated from. Useful for labeling pages in the editor.

**No DB migration needed.** The `layout_data` TEXT column already exists (V30). Format detection at read time: if `data.version === 2` → use `data.pages`; otherwise fall back to v1 single-block-list behavior.

**Backward compat rule:**
- `LayoutRenderer`: if `version === 2`, render carousel; else render single-page (existing behavior).
- `LayoutEditor`: if editing a v2 layout, show page tabs; if editing v1, show single page (as today).

---

### LayoutEditor: Multi-Page Mode

When the wizard starts a "page by page" chapter, `initBlocks` receives a pages array instead of a single block list.

Changes to `LayoutEditor.jsx`:
- Add `currentPageIndex` state (starts at 0).
- Page navigation bar at the bottom: `< Page 1 of 3 >` + "Add page" button.
- Toolbar (Add Text, Add Photo) operates on `pages[currentPageIndex].blocks`.
- Auto-save serializes the full v2 structure: `{ version: 2, pages }`.
- Each page shows the `sourceKey` label in the navigation bar if present (e.g., "First Smile", "Week 8").

---

### LayoutRenderer: Page-Flip Carousel

Changes to `LayoutRenderer.jsx`:
- Detect `layout.version === 2`.
- If v2: render a single page at a time with `currentPage` state + prev/next arrows.
- Page indicator: `"2 / 4"` centered below the canvas.
- Swipe support (touchstart/touchend) for mobile — if swipe delta > 50px horizontal, advance page.
- If v1: existing behavior unchanged.

---

### Wizard: "Page by Page" Mode

**Entry point:** Add a mode selector to the wizard — either at the very start (before period selection) or after entry selection (step 3). The latter is better UX: user picks entries first, then decides whether to write one story or one page per entry.

**Recommended placement:** After step 3 (entry selection), before generation:
- Show a "How would you like to write this?" card:
  - **"One Story"** — current behavior, generates a single combined narrative.
  - **"One Page Per Memory"** — generates a separate paragraph/blurb for each selected journal entry and first time; each becomes its own page in the layout editor.

**"One Page Per Memory" generation flow:**
1. For each selected entry (journal + firsts), call a NEW backend endpoint (or pass a flag to the existing one) that generates a short narrative for just that single entry.
2. Responses come back as an array of `{ sourceKey, body }` objects.
3. The wizard creates a multi-page layout_data v2 structure, one page per entry, each with a text block pre-filled from its generated body (stripped of [PHOTO] markers).
4. Photo slots are added automatically if the entry has a photo.

**Backend:** New endpoint `POST /storybook/{id}/generate-pages` (or a `perEntry: true` flag on the existing generate endpoint). Iterates selected entries, calls ClaudeClient once per entry with a shorter focused prompt (just that entry's text, not the combined batch).

**Wizard state additions:**
- `mode`: `'single' | 'paged'` — set at mode picker step.
- `generatedPages`: array of `{ sourceKey, body }` returned from the server.
