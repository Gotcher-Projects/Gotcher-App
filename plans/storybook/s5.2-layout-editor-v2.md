## Overview

Three concrete features, roughly in order of complexity:

1. **Page reordering** — move pages left/right within a multi-page chapter
2. **Edit mode for published chapters** — "Edit" on a chapter with layout data should open the layout editor, not a textarea
3. **Standalone photo uploads** — add photos to the book that aren't tied to a journal entry or first time

Each is independent — they can be shipped separately or together.

---

## Feature 1: Page Reordering

### Problem
Multi-page chapters generate pages in the order entries were selected, with no way to reorder them after the fact. If the user wants "First Smile" before "First Bath," they're stuck.

### Design
Add **Move Left** and **Move Right** buttons to the page navigation bar in `LayoutEditor`. Only show the relevant button when it makes sense (no "Move Left" on page 1, no "Move Right" on the last page).

Placement: next to the existing `< Page N of N >` nav, e.g.:

```
[ ← ] [ Move ← ]   First Smile · Page 2 of 4   [ Move → ] [ → ]
```

Or a simpler icon-only approach: use `ArrowLeftRight` or dedicated up/down/left/right arrows that feel distinct from the prev/next navigation arrows.

### Implementation

**`LayoutEditor.jsx`**:
- Add `movePageLeft()` / `movePageRight()` functions that swap `pages[currentPageIndex]` with its neighbor and update `currentPageIndex` to follow the moved page
- Add two icon buttons in the page nav bar (only rendered when `multiPage`)

```js
function movePageLeft() {
  if (currentPageIndex === 0) return;
  setPages(prev => {
    const next = [...prev];
    [next[currentPageIndex - 1], next[currentPageIndex]] = [next[currentPageIndex], next[currentPageIndex - 1]];
    return next;
  });
  setCurrentPageIndex(i => i - 1);
}
```

Auto-save fires after the swap (existing `scheduleAutoSave` call).

No backend changes needed — the reordered pages array is just serialized into `layout_data` on the next auto-save.

### Verification
- 4-page chapter: move page 3 to position 1 using repeated Move Left — verify page label follows and content is correct
- Published view: carousel reflects the new order
- Auto-save fires and persists the new order

## Feature 2: Edit Mode for Published Chapters

### Problem
For chapters with `layoutData`, the **Edit** button in `StorybookTab` currently opens a `<Textarea>` for editing `chapter.body` — which is either empty (paged mode) or the wrong field to edit (layout mode). It does nothing useful.

### Design
When `hasLayout` is true, Edit should open the layout editor inline (or in the same modal/sheet used for chapter creation), pre-loaded with the chapter's current `layoutData`.

**Back/cancel** should restore the previous published state without saving.
**Save** should PATCH `layoutData` (and optionally `body`) and stay published.

Two UX options:

| Option | Approach | Complexity |
|---|---|---|
| A | Re-open the wizard at the layout editor step (step 6) | Low — wizard already supports this |
| B | Inline edit: expand the chapter card to show the layout editor | Medium — needs card state management |

**Recommended: Option A** — simplest path. The wizard's layout editor step already has the full editing UI. Pass the existing published chapter as the initial chapter state, skip steps 1–5, and land directly at the layout editor with a "Save" button instead of "Publish."

### Implementation

**`StorybookTab.jsx`** — `ChapterCard` for published chapters:
- Replace the current `setEditing(true)` button with a check: if `hasLayout`, call a new `onEditLayout(chapter)` prop instead of setting textarea edit mode
- `onEditLayout` triggers the wizard opening at the layout editor step with the chapter pre-loaded

**`StorybookWizard.jsx`**:
- Add an `editMode` prop + `initialChapter` prop
- When `editMode=true`, skip steps 1–5 and start at step 6 (layout editor)
- The "Publish Chapter" button becomes "Save Changes"
- On save: PATCH `layoutData` only (no status change, chapter stays published)
- On back/close: confirm discard if unsaved changes

**`StorybookTab.jsx`** parent (`MemoriesTab.jsx`):
- Add `editingChapter` state
- Pass `onEditLayout={ch => setEditingChapter(ch)}` to chapter cards
- When `editingChapter` is set, render `<StorybookWizard editMode initialChapter={editingChapter} ... />`

### Verification
- Published chapter with layout → Edit → layout editor opens with existing blocks
- Move a block → "Saving…" → "Saved ✓" appears
- Close → chapter in book list reflects changes
- Published chapter without layout → Edit → existing textarea behavior unchanged

## Feature 3: Standalone Photo Uploads

### Problem
Photo blocks in the layout editor can only pull from journal entries and first times (via the photo tray). Users can't add personal photos directly — e.g., a family photo, a hospital wristband shot, or anything not captured in the journal.

### Design
Add an **"Upload photo"** option to the photo tray that lets users pick a file from their device. The uploaded photo is:
- Stored in Cloudinary (same pipeline as journal images)
- Associated with the chapter via a new `chapter_photos` array in the chapter record (or stored as a photoOverride with a generated key)
- Available in the photo tray for any block in the same chapter

### Storage approach

**Option A — New `chapter_photos` JSONB column** (simplest):
- `V31__chapter_photos.sql`: `ALTER TABLE chapters ADD COLUMN chapter_photos JSONB`
- Each entry: `{ "key": "upload:uuid", "url": "https://...", "label": "My caption" }`
- PATCH endpoint already exists — just add `chapterPhotos` to `UpdateChapterRequest`

**Option B — Reuse `photoOverrides`** (no migration needed):
- Store uploaded photos in `photoOverrides` under generated keys like `upload:abc123`
- Photo tray already reads `photoOverrides` for display

**Recommended: Option A** — cleaner separation. `photoOverrides` was designed to override specific journal entries, not store net-new photos.

### Upload Flow

In the photo tray (`PhotoTray` component in `LayoutEditor.jsx`):
- Add an "Upload a photo" button at the top of the tray
- On click: trigger a hidden `<input type="file" accept="image/*">`
- On file select: upload to Cloudinary via the existing `/storybook/{id}/upload-image` endpoint (or a new one if that doesn't exist)
- On success: add the new photo to `chapter.chapterPhotos`, close the tray, and immediately assign it to the block that opened the tray

### Backend Changes

- `V31__chapter_photos.sql` — add `chapter_photos JSONB` to chapters
- `ChapterResponse.java` — add `List<Map<String,Object>> chapterPhotos`
- `StorybookService.java` — read/write `chapter_photos`; new `uploadChapterPhoto()` method (Cloudinary upload + append to `chapter_photos`)
- `StorybookController.java` — `POST /storybook/{id}/chapter-photos` endpoint (multipart upload)

### Verification
- In photo tray: "Upload a photo" button appears above journal photos
- Pick a local image → spinner → photo appears in tray and is assigned to the block
- Reload the page → uploaded photo is still assigned (persisted via `chapter_photos`)
- Photo appears in the published LayoutRenderer view

## Potential New Features — Discussion

The following aren't in scope for S5.2 but are worth talking through. Some may be promoted to S5.3 or a later session.

### 1. Chapter reordering in the book list
Currently chapters display in creation order. Users might want to reorder them — e.g., put a milestone chapter at the top. This would require an `order_index` column on chapters and a drag-to-reorder UI in the book list.

**Question for Michael:** Is this something parents would actually use, or is chronological order always correct?

### 2. Duplicate page / duplicate chapter
In the layout editor, a "Duplicate this page" button would let users quickly create variations of a page layout. Similarly, duplicating a whole chapter might be useful for re-running a different period with the same layout preferences.

**Question for Michael:** Dupliating pages feels useful in the editor. Duplicating chapters seems niche — skip?

### 3. Per-page background color
Let each page have its own background color (or a small set of swatches: white, cream, soft pink, sage, slate). Would add visual variety without the complexity of full background images.

**Effort:** Low frontend (one state field per page in v2 format), zero backend (stored in `layout_data`). Could be in S5.2 or S5.3.

### 4. Stickers / decorative elements
Small SVG decorations (hearts, stars, footprints, baby icons) that can be dragged onto the canvas like any other block. A "sticker" block type with a `stickerKey` field referencing a static set of SVGs bundled with the frontend.

**Effort:** Medium. Requires a new block type and a sticker picker UI. No backend changes.

### 5. Text formatting within blocks
Currently text blocks are plain paragraphs. Adding bold, italic, or font-size controls would require either a rich-text editor (Tiptap, Slate) or a custom inline-formatting approach. This is a significant jump in complexity.

**Question for Michael:** Is plain serif text enough for now, or is formatting important to the target user?

### 6. Print / PDF export of the whole book
S8 is already planned for print. Worth noting that the page-flip carousel structure from S5.1 makes this much more tractable — we can render each page at print resolution.

### 7. Book cover page
A dedicated cover page (auto-generated or manually designed) at the start of the book with the baby's name and a hero photo. Could be a locked first chapter or a special chapter type.

**Question for Michael:** Worth investing in for v1, or defer until there's more content to frame?

### 8. Collaborative / family sharing
Let a partner or grandparent view the book (read-only share link already partially planned in S7). An edit-capable share would be a much bigger feature — probably post-v1.
