Security

P1 · SECURITY IDOR — page generation reads entries without owner scoping

StorybookService.buildBatchPagesPrompt:289,310  ·  wizard():143–172 (stores IDs unvalidated)

wizard() stores the client-supplied selectedJournalIds / selectedFirstTimeIds verbatim, with no check that they belong to the caller's baby profile. Later, buildBatchPagesPrompt fetches them with SELECT … FROM journal_entries WHERE id IN (…) and … FROM first_times WHERE id IN (…) — again no baby_profile_id filter. So a user can submit another user's entry IDs and have that content pulled into their own chapter / sent to Claude and returned in the generated pages. Every other read in the service is correctly ownership-scoped — these two are the exception.

Fix: scope both queries by the caller's baby_profile_id (… WHERE id IN (…) AND baby_profile_id = ?), and/or validate the selected IDs against the profile at wizard() time before storing. Add a regression test (pairs with Pass 3). This should be fixed before the branch ships.

P2 · SECURITY Credit check-then-decrement is a race (TOCTOU)

StorybookService.generatePages:212–235

Credits are validated (if (credits < totalEntries) throw…) and then decremented in a separate statement. Two concurrent generate calls can both pass the check before either decrements, overspending credits or driving the balance negative — the same class of bug the jti fix addressed for refresh tokens.

Fix: make it one atomic conditional update — UPDATE users SET ai_credits_remaining = ai_credits_remaining - ? WHERE id = ? AND ai_credits_remaining >= ? — and treat a 0-row result as "insufficient credits."

P2 · SECURITY Upload endpoint accepts arbitrary bytes (no type/size guard)

UploadController.upload:28–43  ·  ImageUploadService.upload:25–31

The controller only checks file.isEmpty(); ImageUploadService streams file.getBytes() straight to Cloudinary with no content-type or size validation. An authenticated user can push non-image or very large payloads (and getBytes() buffers the whole file in memory).

Fix: validate Content-Type is image/* and enforce a max size (a Spring spring.servlet.multipart.max-file-size limit plus an explicit check). Applies to both /upload and /storybook/{id}/chapter-photos.

P2 · PRIVACY Account-deletion photo cleanup misses folders

ImageUploadService.deleteAllForUser:36  ·  UploadController:31–36  ·  StorybookService.uploadChapterPhoto:396

The cleanup folder list is { journal, misc, marketplace, babies, first-times }, but actual upload folders are journal, marketplace, bump_photos, misc, and storybook (chapter photos). So on account deletion, bump_photos and storybook assets are never removed (a retention/GDPR gap), while the list references first-times — a folder that's never written (the first_times context falls through to misc). Three places define the folder taxonomy and they disagree.

Fix: centralise the folder names in one constant, add bump_photos + storybook to deleteAllForUser, and drop the dead first-times entry (or give first_times its own folder in the controller switch).

Error handling & robustness

P2 A couple of controller methods can hit the 401 trap

StorybookController.reorder:37–48, getAll:32–35 (no try/catch)

Most storybook endpoints wrap the service call and map exceptions via ApiError, but reorder and getAll don't. Per the project-wide gotcha, an uncaught RuntimeException re-dispatches to /error unauthenticated and surfaces as a confusing 401 instead of 500.

Fix: wrap them like the others (or add a @RestControllerAdvice to handle this uniformly — a better long-term answer than per-method try/catch everywhere).

P3 Frontend error routing relies on string-matching status codes

StorybookWizard.handleStartPath:233–242

msg.includes('402') || msg.includes('credit') / msg.includes('403') is brittle — it couples the UI to exact error text and HTTP status digits appearing in the message. A structured error (status field) would be sturdier. Also minor: ChapterCard.handlePublish calls onError(...) without optional chaining, unlike most call sites that use onError?.().

P3 PDF export is sequential with fixed per-page waits

storybookPdf.js: captureComponent:53,65 (400ms + 100ms per page)

Each page renders off-screen and waits a fixed ~500ms for fonts/layout/images before html2canvas. For a long book this is slow (linear, blocking). Functionally fine; just flag it as a known cost.

Optional: replace the fixed timeouts with explicit readiness waits already partially in place (document.fonts.ready + image onload) and trim the magic sleeps; the cover capture could overlap.

The same module is imported with and without its .jsx extension, and pregnancy components use relative paths while storybook uses the @/ alias. Harmless but adds friction and noise to diffs/grep.

Accessibility

P3 Custom overlays aren't proper dialogs

imageUtils crop modals (70–132, 160–206) · PhotoTray · ScrapbookBuilder TemplateSheet

These hand-rolled overlays close on backdrop click but have no role="dialog"/aria-modal, no focus trap, and no Esc-to-close. Keyboard and screen-reader users can tab out behind them. (The Radix Dialog used elsewhere handles all this — these predate/sidestep it.)

Fix (incremental): at minimum add Esc handling + role="dialog"/aria-modal; ideally route through the shared Radix Dialog.
